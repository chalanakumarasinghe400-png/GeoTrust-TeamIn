Member 1: Geolocation & Tracking (~350 words / ~2.5 mins)
What to show on slide: A diagram showing the UI asking a LocationTracker class for data.
Script:
"Good morning. I worked on the location tracking subsystem for our GeoTrust mineral transportation platform. In an application like this, tracking the exact route of our transport vehicles is critical.

Instead of writing the GPS code directly into our screen files, I followed Object-Oriented principles and created a separate LocationTracker class. This principle is called encapsulation. By doing this, our user interface simply asks this class for the current location, without needing to know anything about how the phone's hardware actually works. This makes our code highly modular and easy to read.

To track the route of the vehicles, I utilized a standard List data structure to store the history of coordinates. Since we use an existing Flutter library to get the raw GPS data, my main software engineering contribution was controlling when we update the database.

I wrote a logical flow using an if condition to check the distance between the driver's last known location and their new location. If the truck has moved less than 10 meters, the code simply skips the database update. This simple logic is very important because it stops our app from writing to the database every single second, which would waste bandwidth and drain the driver's battery during a long transport trip.

Finally, I handled edge cases and errors. For example, what happens if a driver denies GPS permissions? Instead of letting the application crash, I wrote a simple check using a boolean flag. If the permission returns false, the tracker safely stops and sends a message back to the UI to show a warning to the driver. This ensures the application remains stable at all times."

Script:
"Hello. My role in the GeoTrust project was connecting our application to our Supabase database to store our mineral transport logs and user records safely.

To keep our software architecture modular, I created a dedicated 'Repository' class. This file is the absolute only place in the entire application that communicates with the Supabase database. This is a core Object-Oriented design principle. If we ever decide to change our database in the future, we only have to update this single file, rather than searching through dozens of UI screens to fix broken code.

When our database sends us information—like the details of a mineral shipment—it comes in a format called JSON. Dart reads this as a Map data structure, which is just a collection of keys and values.

My main technical contribution was writing constructor methods inside our data classes to convert these Maps into actual Dart objects. For example, I created a Trip class with properties like tripId, mineralType, and weight. My code takes the raw Map and assigns the values to a new Trip object.

I also added simple error handling here. Sometimes, a database record might be missing a piece of information, causing a null value. I wrote simple conditional checks so that if, for example, the weight is missing from the Map, my code assigns a default value of zero instead of crashing the app. By doing this, the rest of our application works with safe, structured, and predictable objects instead of raw, risky text."

Member 3: Authentication & Role-Based Access (~350 words / ~2.5 mins)
What to show on the slide: A simple flowchart showing a user logging in, the app checking their role, and branching off to either the "Driver Screen" or the "Admin Screen."

Script:
"Good morning. For the GeoTrust platform, my technical contribution was building the user authentication and role-based access system. In a logistics application, security and user permissions are very important. We have different types of users—primarily transport drivers and logistics administrators—and they need to see completely different screens when they open the app.

To build this cleanly, I used Object-Oriented principles and created a dedicated AuthenticationManager class. This class handles all the login, registration, and logout processes. By encapsulating this code into its own class, our login screen widget just calls a simple login() method. The visual screen doesn't need to know anything about the complex security protocols happening behind the scenes, which keeps our codebase modular and easy to manage.

When a user successfully logs in, the server returns their profile data in a Map structure. My main logical contribution was extracting the 'user_role' text from this Map and using it to safely guide the user through the app.

I wrote a routing algorithm using if-else conditional statements based on this role. If the text exactly matches 'driver', the code programmatically changes the navigation stack and sends them to the Driver Dashboard, where they can see their assigned mineral pick-ups. If the role equals 'admin', the code routes them to the Admin Control Panel, where they can view the live locations of all trucks. This strict logical flow ensures users cannot access unauthorized areas of the software.

Finally, I implemented a safety net using a try-catch block for the login process itself. When a user tries to log in, many things can go wrong. If they enter the wrong password, the network throws an error. Instead of letting the application crash on the login screen, my catch block intercepts that error. It reads the error code and uses a simple switch statement to display a friendly warning message on the screen, like 'Incorrect Password' or 'User Not Found.' This guarantees the application remains stable and user-friendly at all times."
Member 4: App State & Caching (~360 words / ~2.5 mins)
What to show on slide: A diagram showing a Try/Catch block deciding whether to use Supabase or the Local Cache.
Script:
"Hello. My technical focus for the GeoTrust platform was managing the application's data state and building an offline caching system. Mineral transport vehicles frequently travel into remote areas like mining sites where there is no 4G connection.

To handle this, I used the shared_preferences library, but to keep our architecture clean, I built a custom LocalCache class around it. When a driver is assigned a new route, my code takes those trip details and saves them directly to the phone's local storage. This data is saved using simple key-value pairs—for example, the key might be 'current_trip' and the value is the text data of the route.

The most important part of my work was writing the logical flow to use this cache. Whenever the app tries to load data, I wrapped the network request in a try-catch block. First, the code tries to fetch the live data from our Supabase server. If the phone has no internet, that network call fails and throws an error.

Instead of letting the app crash, my catch block intercepts that error. It immediately runs the backup code, which reads the saved key-value pairs from the LocalCache class, and passes that saved data to the user interface. Because of this Object-Oriented design, the UI doesn't even know the app is offline—it just receives the data and displays it. This ensures the driver can always see their route, even without a signal."
